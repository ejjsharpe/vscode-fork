## Problem Statement

Developers working across several projects and agent conversations need to move between independent workspaces without losing their editing context, stopping background work, or navigating unrelated native windows. They also need to continue the exact same conversation from either a shared Agents view or its project's editor, with a reliable route to the files the agent is actually changing.

The current desktop implementation and Agents handoff still contain assumptions that one workbench owns one native window, that session identity is enough to reopen a conversation, and that presentation lifetime can stand in for execution lifetime. Those assumptions do not satisfy the accepted combined-window behavior, especially for multi-folder workspaces, worktrees, remote environments, project closure and recovery.

This spec synthesizes the approved [One-window IDE with project tabs and shared Agents decision map](https://github.com/ejjsharpe/escode/issues/16). The [final audited design approval](https://github.com/ejjsharpe/escode/issues/22#issuecomment-6478807512) is complete. BrowserWindow with retained WebContentsViews remains the provisional architecture candidate; runtime feasibility is explicitly unproven. There is no Stage 1 or overall feasibility pass.

## Solution

Provide a new standalone IDE with one shared shell containing a permanent Agents button to the left of a Chrome-like strip of project tabs. Each project tab represents a complete independent workspace, including single-folder and multi-folder workspaces. Switching views preserves its editors, unsaved changes, terminals, Git context, tasks, debugging and agent work.

Within a project, offer Project Chats alongside Files and Source Control. Selecting a conversation opens a chat editor in the central editor area beside file editors. Agents and that chat editor present the same provider-owned conversation. Go to project opens or selects its exact home workspace and exact chat; Show in Agents returns to that conversation without losing presentation state or repeating work.

Preserve the existing editor and Agents interiors as the baseline, using the [creator-approved interaction prototype](https://github.com/ejjsharpe/escode/issues/21#issuecomment-6464329809). Make project closure, reload, recovery, opening, restoration and native command routing honor the independent lifetimes of the shared shell, each project and provider-owned execution. Start with fresh app-owned state, while allowing normal discovery of provider-owned history.

## Implementation Decisions

1. **Retain the accepted architecture candidate.** Use one native BrowserWindow with the shared shell in its primary renderer and separate retained WebContentsViews for the real Agents workbench and each independent project workbench. Switching changes selection, bounds, visibility and focus without rebuilding a workspace. The candidate remains provisional pending the separate runtime gate; separate WebContents do not guarantee separate renderer processes or universal crash isolation.
2. **Keep ownership explicit.** The shared shell owns top-level navigation, order, selection, its stable profile/theme and aggregate attention. Main-process hosting owns native attachment, bounds, authenticated mappings, native routing and lifecycle coordination. Each project owns its workspace configuration/storage/trust, profile, extensions, editors, Git, terminal/task/debug services and remote authority. The persistent Agents environment owns Sessions orchestration and presentation. Each existing provider remains authoritative for its conversations, transcript, execution and recovery.
3. **Reuse the existing layering and service boundaries.** Shared hosting belongs at the platform/native-window boundary. Provider-neutral chat view and command contracts belong in Workbench or lower layers, with Sessions-owned adapters composed above them. Sessions may depend on Workbench; Workbench must not depend on Sessions. Shared consumers must not import provider implementations. Preserve the existing provider registry, model-management and visible-session service responsibilities, observables, contribution registration and editor-opening services.
4. **Make durable workspace and per-chat home identity explicit.** A single-folder workspace is its exact folder plus environment; a saved multi-folder workspace is its exact workspace file plus environment. Different worktrees and local/SSH/Dev Container authorities remain distinct. Persist one home per project-associated chat through the provider-neutral contract; distinguish unresolved metadata, intentional No Workspace and a recorded home. Session membership, folder containment and repository similarity confer no additional home. Reuse existing persistence mechanisms rather than introducing a second transcript store.
5. **Route the exact conversation.** Carry provider, session resource, exact selected chat resource when known, and home workspace through the shared routing contract. Resolve provider redirects through the owning provider; consumers do not parse provider URI formats. Reuse an exact existing project tab, choosing its most recently active match if duplicates already exist, or open the exact home. Reveal that exact chat through the editor service. A session-only legacy link cannot promise an exact chat it did not identify.
6. **Use one conversation authority with multiple presentations.** Renderer-local models may project provider-owned state. Send, cancel and approval operations retain the exact identity and owner. Preserve unsent input, attachments, model choice, reading position, streaming and approvals across renderers, including switches before a debounced draft write completes. Navigation must not create a new conversation, persist a competing transcript, claim execution or repeat a mutation.
7. **Separate agent execution from project presentation.** Before project teardown, the persistent owner must retain or acquire the agent's necessary tools/client connections and approval observation under existing permissions. Actual closure releases the project workbench. Retaining the entire closed workbench, leaving a backend without its tool executor, or broadening workspace/trust permissions does not satisfy continuity. Agent Host evidence cannot establish Copilot Cloud or provider-wide continuity.
8. **Integrate Project Chats and the accepted navigation composition.** Add project-scoped chat membership beside Files and Source Control, chat editors beside file editors, Go to project and Show in Agents. Preserve independent sidebar/editor context, path disambiguation, independently scrolling strips and the permanent Agents entry. Existing editor/Agents interiors remain the baseline. Preserve accessible controls, platform conventions and the repository's design system; no new shortcut scheme was selected.
9. **Preserve tab and attention rules.** New projects append on the right; users can reorder them. Active Close selects the right neighbour, then left, then Agents; inactive Close preserves selection. Inactive projects remain live. Project indicators show project attention; Agents aggregates agent attention, including closed-home conversations. Completion alone is a quiet indicator; routine output stays local and attention never steals focus.
10. **Reuse real project safeguards.** Project Close/reload invokes save, backup/Hot Exit, terminal/task/debug and cancellation handling. Failed save/backup or a genuine veto prevents destructive teardown. Reopening restores recoverable state without restarting ended work. Agent execution follows its independent ownership. Native whole-window Close and app quit coordinate all hosted workbenches and the persistent agent owner before host teardown, with cancellation preserved. Survival of local execution after app quit is not promised.
11. **Separate native host, logical workbench, durable workspace, document and connection lifetimes.** Main owns registrations linking actual Electron senders and current document/connection lifetimes to their workbench, host, role and permitted scope. Caller-supplied IDs, generic handshake context and selection cannot establish authority. An Electron session partition is not workspace, trust or profile isolation.
12. **Enforce authority at the shared native boundary.** Authenticate and scope generic service dispatch and subscriptions, direct IPC, auxiliary ownership, internal/shared-process roles, replies and port transfers before effects. Own-workbench operations derive their target from the binding; explicit and nested selectors require operation-specific permission. Shell/Agents/project coordination uses named operations with existing safeguards, not unrestricted cross-project native access. Preserve explicit application-wide capabilities and sandbox/preload, origin, frame and payload validation.
13. **Use main-owned generations and revocation.** Initial and replacement documents receive fresh non-reused generations through main-controlled bootstrap, independent of reused Electron objects. Connections have their own lifetime. Bind handles, subscriptions and asynchronous work to their originating authority; recheck before subsequent effects, publication, events, replies or ports. Dispose late renderer-owned resources after expiry and reject foreign, unknown and stale access explicitly without redirecting to the selected or replacement view. Already-completed effects are not promised to roll back. Tab switches and same-document activity do not replace a generation.
14. **Preserve cleanup access and authenticate lifecycle replies.** Keep authorized outgoing access available through before-unload safeguards and will-unload joiners. Validate the exact sender/workbench/document, pending operation and expected phase before consuming a reply listener. Invalid, duplicate, guessed, stale or transition-time replies must leave the legitimate pending wait intact. After valid final cleanup acknowledgement, revoke before replacement/destruction. A veto preserves current authority. Crash, destruction or unexpected replacement revokes immediately and retires waits as interrupted; a replacement cannot finish its predecessor's operation.
15. **Confine intentional project recovery.** Only the main host coordinator intentionally destroys the shared native window. Project close, reload and recovery own that project's view/resources and must not trigger neighbouring cleanup. Replace the failed exact workspace/environment/profile with fresh authority, retire old references/listeners/resources, restore recoverable state and reconnect surviving work without replay. Keep a failed replacement identifiable with Retry and Close. Distinguish project failure, Agents/shell failure and actual host loss; no automatic whole-window restart fallback or promise that execution survives its own owner's loss.
16. **Serialize recovery and retain explicit Close intent.** Allow at most one recovery per project. An authorized Close during recovery or host shutdown records one pending Close, invalidates recovery immediately, coalesces repeats and disables Retry while pending. Obsolete callbacks cannot attach/select a replacement, overwrite state or resurrect a tab. Defer competing project teardown while host coordination owns it. Successful host shutdown fulfills Close once; genuine host veto/cancellation preserves Close for normal project safeguards afterward. A project veto clears pending Close but keeps recovery cancelled until explicit Retry. Interruption retains its distinct outcome and requires reconciliation of surviving state.
17. **Make disposal and Close completion truthful.** Capture cleanup identity before destroying views. Continue independently safe bookkeeping when a resource is already gone; surface genuine errors. Retire registration/counts, owned listeners/resources and restoration entries, repair selection/routing, and deliver logical-close notifications consistently once. Expired projects must never alias shell or neighbour identity. Keep one authoritative result per Close attempt independently of live-registry membership, shared by overlapping requests, direct disposal and host coordination. Success requires actual teardown and bookkeeping; registry absence or an already-destroyed view is insufficient.
18. **Preserve distinct lifecycle outcomes and exact-document readiness.** Carry completed disposal, genuine safeguard cancellation, interruption and cleanup failure through transport, unload, Close and host coordination. Readiness means the exact authenticated current document can receive lifecycle safeguard requests; bootstrap authorization, DOM readiness and inherited readiness are insufficient. Close while replacement safeguards are not ready promptly reports Close interrupted to all joined callers. Late readiness cannot retry it. After interruption/failure, only a later explicit attempt may continue unfinished work using surviving state without replaying completed phases/notifications, rewriting the prior outcome, reviving authority or resuming cancelled recovery. Reload and workspace-opening callers must also prevent unsafe replacement after interrupted permission/cleanup.
19. **Route selected-project commands and preserve configuration scope.** Save, terminals, Git, debugging, workspace settings and native menu actions follow the selected project. Native focus restores that view; Agents requires explicit project targets. Workspace settings remain local; shared-profile settings affect projects using that profile; application settings remain global. Agents and shell profiles/themes remain stable. A required profile reload affects only its project.
20. **Apply the final profile-target clarification.** An explicit launch for an already-open exact workspace/environment with another profile reuses that tab and runs the project-scoped profile-change safeguards. Cancellation preserves the original tab/profile and reports the request incomplete; it does not ignore the requested profile, create a duplicate, change neighbours/the shell or queue an automatic retry. Independent agent permissions and lifetimes remain intact.
21. **Establish fresh app-owned identity and storage.** Separate application/runtime identity and app-owned user data, extensions/shared storage, preferences and recovery state from VS Code, Code - OSS and development profiles. Opening an existing source folder is allowed; importing another app's settings, window records, backups or chat database is not required. Normal connected-provider history discovery remains allowed without a history importer.
22. **Apply startup preferences to this app's project tabs.** Restore saved order, permitted set, selection and recoverable conversation presentation; explicit launch targets take selection priority and unknown selection falls back to Agents. Preserve the existing modes: preserve restores the saved set even with an explicit target; all restores it on ordinary startup; folders restores folder/workspace tabs; one restores the previously selected view; none opens Agents without prior projects. Retain existing explicit-launch behavior for all/folders/one; explicitly requested targets still open. No mode discards recoverable unsaved work, including untitled/empty workspaces. A deliberately closed tab is not reopened merely for its chat history.
23. **Integrate ordinary opening entry points and CLI lifetimes.** Route ordinary workspace opening into the shared shell. New Window becomes new-tab behavior; untargeted requests create an empty tab and exact existing targets reuse their tab. Extension-development host windows remain separate. Reuse Window sends file operations to the active project; explicit workspace requests select/open that target without replacing an unrelated project. Open Agents selects Agents. Preserve explicit profiles, remote targets, file/line and diff/merge arguments. --wait belongs to the relevant files/workbench condition, not shell lifetime, view selection or unrelated project closure.
24. **Preserve link and discovery semantics.** Draft links do not send or overwrite occupied drafts/attachments; omitted workspace on an agents/new link retains intentional No Workspace semantics. Provider discovery preserves recorded homes, waits for loading metadata and assigns automatically only with one exact home. Ambiguous ownership offers non-blocking Choose Project when opened or navigation is requested; no startup bulk wizard. Assignment associates the existing conversation without copying or sending; weaker later metadata cannot overwrite an explicit choice.
25. **Recover unavailable exact targets explicitly.** Keep saved targets identifiable with Retry/Close while neighbours remain usable. Offer reconnect/sign-in for remote targets and Locate/Restore for missing folders, workspace files or worktrees where supported. Preserve backups and the conversation in Agents. A replacement environment/workspace requires explicit reassignment; never substitute a local copy, similar repository or main checkout. This does not guarantee reconstruction of a deleted worktree or replay requests/approvals.
26. **Measure capacity before setting resource budgets.** Evaluate 3–5 projects as normal and ten as an upper-end workload; ten is not a hard cap. Target roughly 200 ms warm switching, measure memory/CPU and genuine background progress, and seek low idle CPU without automatically suspending or closing projects. New-project opening may take longer. No numerical resource budget or achieved performance claim is established yet.
27. **Reach all affected integration surfaces without duplicating subsystems.** The implementation spans native hosting/bootstrap/lookup and IPC; logical and native lifecycle, recovery and disposal; workspace opening, launch arguments, --wait and restoration; native focus/menu/dialog/status routing; profile/storage/trust and extension/utility/terminal ownership; provider-neutral chat routing, home metadata and presentation handoff; Project Chats/editor and shell contributions; fresh app identity/configuration; and the corresponding callers, registrations, fixtures and tests. Inspect existing adapters before adding code and use existing bounded services. No new general recovery or authorization framework is selected.

The accepted rules above derive from [chat ownership](https://github.com/ejjsharpe/escode/issues/17#issuecomment-6456724688), [project lifecycle](https://github.com/ejjsharpe/escode/issues/18#issuecomment-6464014913), the [hosting decision and its accepted refinements](https://github.com/ejjsharpe/escode/issues/20), [fresh-app behavior](https://github.com/ejjsharpe/escode/issues/24#issuecomment-6464720430), and the [final audit and approval](https://github.com/ejjsharpe/escode/issues/22#issuecomment-6478807512). Their owning resolutions remain authoritative. Later accepted refinements take precedence over historical migration assumptions, stop-on-failure directions and requirements that runtime validation block design-map closure. This synthesis does not waive a detail omitted from its summaries.

## Testing Decisions

The creator confirmed the proposed test boundaries during this spec preparation: test primarily through the real desktop app with Agents and two independent projects, backed by focused existing service tests for hard-to-reproduce races. The complete [runtime validation contract in #35](https://github.com/ejjsharpe/escode/issues/35) and its [frozen inherited acceptance contract](https://github.com/ejjsharpe/escode/issues/33#issuecomment-6478223824) remain required.

- **Primary boundary:** launch the real Electron app with the shared shell, real Agents, one single-folder project and one saved multi-folder project. Drive user-facing commands and observe actual work, files, conversations, processes and lifecycle outcomes. Reuse existing desktop Electron/Playwright launch, driver and smoke-test infrastructure, extending hosted-view targeting only where needed. One application-level acceptance boundary is preferred over a new harness per module.
- **Good tests assert observable contracts.** Verify the selected exact workspace/chat, preserved state, real safeguard outcomes, continued work, explicit access rejection, absence of duplicate effects and truthful completion. Do not assert private fields, implementation call order or a particular counter design as a substitute for these outcomes. Diagnostic identity/resource observations support cross-process assertions where the UI alone cannot establish them.
- **Focused service tests support deterministic regressions.** Reuse the existing native lifecycle veto/joiner tests, window-state restoration tests, Agents editor-handoff tests and ChatEditorInput tests. Exercise public service boundaries for exact routing, startup/profile semantics and controlled asynchronous lifecycle/recovery races. Use existing dependency-injection fixtures, deferred operations and disposal-leak checks; avoid new test-only production abstractions. Real desktop checks remain necessary for native sender identity, resource ownership and actual cleanup.
- **Mocked web tests have a limited role.** The existing Sessions E2E suite uses a real workbench with mocked account/auth, agent and backend services. Reuse it for deterministic presentation/navigation regressions where useful; it cannot prove native retained-view hosting, real provider continuity or actual save/process behavior. The clickable prototype likewise establishes interaction direction only.
