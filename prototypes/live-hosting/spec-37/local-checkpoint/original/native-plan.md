## #40: required reach, in dependency order

1. Extend the existing `prototypeLifetime.ts` registration/binding with main-owned role and configured workspace/environment scope. It currently stores only contents/generation/workbench, so it cannot distinguish Agents/project/auxiliary capabilities. Pass these from actual CodeWindow registration, never the generic handshake or current selection. Preserve current document readiness/revocation.
2. Add shared/PTY/agent-host requests, restart and OTel policy to protected preload credential forwarding (`base/parts/sandbox/electron-browser/preload.ts:128–143`). Validate sender/main frame/exact payload/current generation before startup or mutation in `SharedProcess.onWindowConnection`, `ElectronPtyHostStarter._onWindowConnection`, `ElectronAgentHostStarter._onWindowConnection` and restart/policy listeners. All currently accept correlation nonce without protected document credential; destroyed checks do not detect reload. Capture generation before async start and recheck before reply/port/error publication. Close late ports.
3. Carry authenticated context in existing `UtilityProcess.connect(payload)` transfer to `base/parts/ipc/node/ipc.mp.ts`. That server currently discards parent payload and allows the renderer IPC handshake to establish context. `ClientConnectionEvent.context` already permits trusted context, so reuse it. Preserve special raw shared-process connection routing when changing payload from response-channel string to a structured trusted envelope.
4. Revocation after port transfer needs an actual mechanism. Acquisition gating alone is insufficient. A bounded main-to-utility revoke message tied to main-issued connection identity, with utility-server retained ports/cleanup, can reuse existing UtilityProcess messaging; alternatively retain a main port relay. Do not broadly expose another global authorization framework. Test actual stopped calls/events and late resource cleanup.
5. Scope both PTY paths: generic `createLocalPtyChannel` and direct `PtyHostWindow` in `ptyHostMain.ts:93–100` currently share unrestricted ProxyChannels. Validate process IDs, workspace/layout/revive/detach IDs against trusted owner, filter events and results, and keep legitimate same-workspace persistent restoration distinct from stale-document access. Global shutdown/restart/auto-replies/kill-port need named coordinator permission. Caller `window:<id>` handshake is not authority.
6. Agent Host Management is a raw full ProxyChannel at `agentHostMain.ts:521`; restrict role/session/resource scopes there as well as protocol/reverse channels. Restart/policy currently ignore event origin. Main management connection uses string context `'agentHost'`; `registerConnection()` at 306–323 treats every nonempty string as a renderer and installs reverse proxy/BYOK bridges. This explains prior `Unknown channel: agentHostClientProxy` startup output: classify trusted main management separately, rather than suppressing errors or exposing renderer channels.
7. Existing extension host adapter cleans late creation. Worker adapter records ownership before await, then only `prototypeBinding(context)` after creation: verify and repair the late-create versus early-dispose race so a worker created after revocation is disposed again. `onPrototypeConnectionRevoked` listeners in wrappers are currently not attached to returned disposable owners; use the existing app registration disposable lifecycle.

Primary focused seams already present: `platform/terminal/test/common/localPtyChannel.test.ts`, `terminal/test/node/{ptyService,ptyHostService}.test.ts`, `workbench/contrib/terminal/test/electron-browser/{localTerminalBackend,localPty}.test.ts`, `platform/agentHost/test/{electron-browser/localAgentHostService,node/protocolServerHandler,node/agentHostService}.test.ts`. Existing common IPC test patterns can cover trusted parent context and post-revoke port delivery. Native acquisition needs an Electron boundary fixture, not an internal-map assertion. Real heartbeat, extension command, task/debug/Git progress belongs to a bounded ordinary desktop scenario; it is separate from #35's full native matrix.

## #41: native routing has a concrete host-ID failure

`menubar.ts:792` obtains a native BrowserWindow, then calls `windowsMainService.getWindowById(activeBrowserWindow.id)`. Hosted logical windows use 100000+ IDs, so native menus cannot find the selected hosted workbench. Native focus events in `NativeHostMainService` similarly filter native BrowserWindow IDs through logical lookup and drop them. Resolve the actual selected logical view of that host through the shared-host owner. When Agents is selected, project-specific commands need an explicit target; never fall back to the last project.

`sendWhenReady` / queued dialog callbacks need originating contents+generation captured before await/queue, rechecked before delivery/effects. Do not queue a stale command to a replacement. `DialogMainService` queues per native host ID, so hosted project identity must be carried by its caller before entering that queue and revalidated before showing; merely targeting the shared BrowserWindow cannot establish project context.

Auxiliary registration at `auxiliaryWindowsMainService.ts:83–89` trusts `mainWindowId`. Record parent from the actual opener. Its current `did-create-window` listener is attached to native window primary WebContents; retained workbench contents need the same registration path. `IAuxiliaryWindowsMainService.createWindow(details)` currently has no opener argument. Extend that existing API/callers with main-established parent ownership rather than letting auxiliary preload declare its parent. Auxiliary role must stay restricted. #39 already plans the BaseWindow focus correction; do not duplicate it.

Generic native allowlist also blocks ordinary `openWindow`, `openEmptyWindow`, `openAgentsWindow`, and `quit`; classify named coordinator operations with explicit targets/safeguards. Do not add unrestricted target IDs to `ownMethods` to make errors disappear. Existing bootstrap/direct zoom/DevTools/environment adapters already capture/recheck generation; preserve them.

## #42–45: retain the existing lifecycle coordinator, repair outcomes

- `LifecycleMainService.close()` at 451 returns `Promise<void>`. A genuine veto returns from `finishPrototypeClose()` but its finally completes the promise, indistinguishable from teardown. Carry cancelled/interrupted/failed/completed outcomes through all callers and transport. Reuse the existing pending map independent of registry; do not add another close manager.
- `CodeWindow.reload()` at 1528 replaces unavailable workspace with undefined after `validateWorkspaceBeforeReload()`. Preserve the exact unavailable workspace and expose failure/recovery instead. `doReload()` at 615 does not await `window.reload(cli)`; await and propagate it, ensuring interrupted cleanup never opens a replacement.
- BaseWindow logical close emits `onDidClose` before all object disposal can fail (`finishLogicalClose:207`). Therefore registry absence/onDidClose cannot certify completed disposal, nor release a wait. Keep one authoritative completion for overlapping/direct/host requests after independently safe cleanup and bookkeeping.
- Existing host coordinator asks all before cleanup and retains `completedHostCleanup`, pending project intent and recovery cancellation serials. Preserve those. Its host completion also needs explicit genuine cancellation versus interrupted readiness versus cleanup failure; current app-quit boolean veto collapses them.
- Existing recovery is already exact-target/profile clone + serial/token dedup + fresh view authority + no replay. Integrate ordinary shell actions; avoid a new recovery subsystem. Existing `setPrototypeClosePending` cancels recovery immediately; keep it cancelled after veto until explicit Retry.
- A failed replacement must stay identifiable. Readiness means current authenticated lifecycle receiver, not DOM or stale isReady. Do not automatically retry when ready arrives.

No platform main lifecycle test directory currently exists. The confirmed renderer seam is `workbench/services/lifecycle/test/electron-browser/lifecycleService.test.ts` (veto/joiners); it cannot establish main-host coordination. Existing Electron `windowImpl.test.ts` plus actual bounded desktop lifecycle scenarios support this; deterministic main-service DI tests should exercise public close/unload outcomes with deferred real service fixtures, not private maps.
