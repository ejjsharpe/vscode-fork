## Existing behavior to retain

- `prototypeLifetime.ts` issues main-owned generations, authenticates sender/frame/nonce, revokes immediately on crash/navigation/destruction and records lifecycle readiness on the current authenticated connection.
- `LifecycleMainService.waitForPrototypeLifecycle` uses per-phase random callback channels with ordinary listeners, rejects invalid messages without consuming the legitimate wait, and retires waits on the matching generation's revocation. `doUnload` retains outgoing authority through permission and joiners, then revokes after final valid acknowledgement. Not-ready unload returns `interrupted`.
- Close publishes its pending record before `setPrototypeClosePending`, checks that record before live registration, and coalesces direct healthy disposal via `CodeWindow.disposePrototypeWorkbench`. Recovery cancellation/serials and host arbitration already exist; extend rather than replace them.
- `BaseWindow` captures hosted contents before destruction, publishes a disposal promise before synchronous reentry, and has separate logical identity with no shell fallback. Host cleanup remembers already acknowledged documents. Preserve these protections.
- #40's read-only `isPrototypeClosePending` getter and named PTY restart coordinator, and #41's selected native routing, must continue to work.

## Missing behavior found in inspected source

1. **Normal project-tab Close is absent.** `createPrototypeWorkbench` creates no `entry.close`; shell markup only renders Close when this callback exists. All callbacks come from recovery/error UI; `setPrototypeRecovery(id, undefined)` clears the callback again after recovery. Wire the existing project Close coordinator into every normal project tab. Keep ordinary Close Window/native close as whole-host Close.
2. **Inactive safeguard visibility/selection needs coverage.** Host Close focuses the workbench before asking it; project Close does not. A real prompt in an inactive project can therefore be hidden. Show safeguards for their owning project and preserve the originally selected view when an inactive tab closes or cancels. Active Close chooses right project, then left project, then Agents; verify project order independently of Agents registration order. Current `removePrototypeWorkbench` simply chooses neighbouring map entries.
3. **Outcome transport is incomplete.** `close(): Promise<void>` resolves both a genuine veto and actual completion. Interruption is a distinct error, cleanup failure another error; these distinctions are not a complete explicit caller contract. Preserve completed/cancelled/interrupted/cleanup-failed across Close, direct disposal, host coordination and reload/opening. Use the smallest existing result/error vocabulary and update all affected callers/fixtures; do not add a general state-machine framework.
4. **Renderer will-unload errors can become success.** `NativeLifecycleService.handleWillShutdown` logs rejected default/last joiners and still returns; its IPC listener then fires `onDidShutdown` and sends success. Surface real cleanup failure through the authenticated phase reply, continue independently safe last cleanup, and avoid certifying completed cleanup. Existing lifecycle test explicitly expects a rejected joiner to be handled, so update behavior/test together. Preserve cancellation and disposable cleanup.
5. **Partial disposal can skip safe bookkeeping or split authority.** `BaseWindow.disposePrototypeWorkbench` skips `finishLogicalClose` if `contents.close` throws. `CodeWindow` bypasses `LifecycleMainService.close` when contents are already destroyed, so direct disposal and a pending main Close can hold different promises. Main Close accesses `window.webContents` while live registry membership can outlast destroyed contents. Preserve one attempt outcome across these paths independently of registration, continue safe detach/registry/count/listener/restoration/routing cleanup, and retain unfinished progress for a later explicit attempt. Never let registry absence imply success; do not replay acknowledged unload or logical-close notifications.
6. **Reload races remain.** `doReload` checks Close/host state only before awaiting unload; it then invokes async `window.reload()` without awaiting it, while `ICodeWindow.reload` declares `void`. A Close may join the same unload and race replacement. Recheck intent/current document after awaited boundaries and await replacement preparation so failed/asynchronous reload cannot leak. Keep missing readiness/interruption blocking replacement and no automatic retry. `windowsMainService`'s existing LOAD caller already uses `if (!veto)`, so preserve that when extending outcomes.
7. **Exact missing-target reload is a related boundary.** `validateWorkspaceBeforeReload` returns `undefined` for a missing folder/workspace file, causing an empty-workspace reload. This violates exact-target/no-substitution. Coordinate with the unavailable-target/opening owner before duplicating work; at minimum #42 reload must not silently replace the project or discard its recoverable state.
